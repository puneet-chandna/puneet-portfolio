2. The Logic Strategy (The "Flexbox" of Terminal)
In the browser, you use CSS Flexbox to handle different screen sizes. in Go (Bubble Tea), you use a library called lipgloss (part of the Charm stack) to do the exact same thing.
Here is the logic flow for how the app renders a frame:
Step A: The Data Model (State)
Your app needs to store the width and height of the user's terminal window because terminal windows can be resized at any moment.
    • Global State:
        ◦ WindowWidth: (e.g., 120 chars)
        ◦ WindowHeight: (e.g., 40 lines)
        ◦ ActiveTab: (e.g., "Projects")
        ◦ CursorRow: (Where the user is looking)
Step B: The Render Math
Every time the user resizes the window, the app recalculates the pane sizes immediately.
    1. Sidebar (Left):
        ◦ Width: Fixed (e.g., 20 chars).
        ◦ Content: Render the Menu List.
        ◦ Border: Right border enabled.
    2. Inspector (Right):
        ◦ Width: Fixed (e.g., 25 chars) OR hidden if WindowWidth < 80 (Responsive Design!).
        ◦ Content: Render details based on what is selected in the center.
        ◦ Border: Left border enabled.
    3. Viewport (Center):
        ◦ Width: WindowWidth - SidebarWidth - InspectorWidth. (It takes up whatever is left).
        ◦ Content: The actual page content.
        ◦ Logic: If the text is too long for this width, word-wrap it automatically.

The State Machine:

Ghost cursor  (opional and will be implemented later ) :
1. The Core Concept: " The Radar Room"
Normally, when you run a Go program, it’s a single process. When you use the wish library for SSH, it creates a separate, isolated sandbox (a Goroutine) for every user who connects.
    • Problem: User A (Session 1) cannot see the memory of User B (Session 2). They are in parallel universes.
    • Solution: We need a Shared Global Object (The Radar Room) that exists outside the individual user sessions. All sessions will report their coordinates to this room, and the room will broadcast updates to everyone else.
2. The Data Architecture
We need a central struct that lives in main.go and persists as long as the server is running.
A. The "Ghost" Data Structure
Every connected user is represented as a "Ghost."
Plaintext
Ghost Object:
  - ID: "Session-X12" (Unique string)
  - X: 12 (Column position)
  - Y: 4  (Row position)
  - Color: "#FF00FF" (Assigned randomly on connect)
  - LastActive: Timestamp (To kill zombies)
B. The "Global State" (The Source of Truth)
This is a Map protected by a Mutex (a lock). You must use a lock because if two users move at the exact same nanosecond, they could crash the server by trying to write to the map simultaneously.
Plaintext
GlobalState:
  - Mutex (Lock)
  - Users: Map[SessionID]Ghost
  - BroadcastChannel: A pipe to send messages to everyone
3. The Logic Flow
Here is the step-by-step lifecycle of a Ghost signal.
Phase 1: Connection (Spawn)
    1. User connects.
    2. Server generates a random color (e.g., Neon Blue) and a Session ID.
    3. Server adds this user to the GlobalState map.
    4. Broadcast: The server yells to all other active sessions: "New Ghost Spawned!"
Phase 2: Movement (The Transmitter)
This happens inside the user's Update() loop (Bubble Tea).
    1. Input: User presses Down Arrow.
    2. Local Update: The UI moves the cursor down on their screen.
    3. Transmission: The app fires a message to the GlobalState:
        ◦ "Session X12 is now at Row 5, Col 0."
    4. Note: This must happen fast. We are treating this like a multiplayer game packet.
Phase 3: The Broadcast (The Receiver)
This is the tricky part. Your TUI needs to listen for updates while waiting for keyboard input. Bubble Tea handles this via Commands.
    1. Every session has a background listener (a Goroutine) subscribed to the GlobalState.
    2. When GlobalState receives a position update, it pushes that data down the Broadcast Channel.
    3. The Trigger: Your Bubble Tea app receives a specialized message: type GhostUpdateMsg struct.
    4. The Render: The View() function redraws the screen:
        ◦ Layer 1: Draw the background/text.
        ◦ Layer 2: Draw my own cursor >.
        ◦ Layer 3: Loop through the GlobalState map and draw a colored block █ at the (X, Y) coordinates of every other user.
Phase 4: Disconnection (The Cleanup)
If you forget this, your server will be full of frozen "ghosts" that never leave.
    1. Event: SSH connection drops (User closes terminal).
    2. Action: The server detects Signal: Terminated.
    3. Cleanup: Remove the Session ID from the GlobalState map.
    4. Broadcast: Tell everyone else to stop rendering that ghost.
4. Visual Representation (The "Cool Factor")
To make this look like a hacker tool, we shouldn't just show a block. We should style the ghosts:
    • The Cursor: A block character (█) in their assigned color.
    • The Label: A tiny, dim text label next to the cursor showing their IP location (anonymized).
        ◦ Example: █ [US-East] or █ [Guest-2]
    • The Trail (Advanced): If you are feeling ambitious, you can leave a "fading trail" where the ghost was 1 second ago, creating a fluid motion effect.
